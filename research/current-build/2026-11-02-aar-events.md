## Method

`instrumentation/aar_events.py` parses each JSONL line strictly, pairs every
`impact_apply_candidate` (`0xc9f910`) enter/leave by `(thread_id, call_id)`, and
recomputes the changed field from the recorded reads. It fails closed on a hash
mismatch, missing header/summary/end record, non-zero suppressed/error/stack
counters, a sampled impact hook, missing pair, failed or indirect read, address
mismatch, non-contiguous ordinal, unsupported mode, a field change that does not
match the mode, a non-increasing accumulator, or effective damage above its
input. It never writes to the trace and never converts wall-clock time to a
frame or simulation clock.

The `0x190`, `0x19c` and `0x1a0` values below are direct float32 reads. `0x194`
(`MaxDamages`) is not in the hook read set and stays `null`; no derived maximum
is promoted to an observation.

An impact-module address below the image base (`0x400000`) is also a
reconstruction failure: the CLI prints `aar_events: module address below image
base:...` and exits 2 with no output files, so no address can reach the
image-offset arithmetic as `None`.

## Referential integrity and the classified file

The extractor enumerated its own 28 events and compared each one with the 28
entries in the previously published classified timeline. All 28 matched on
ordinal, call id, thread id, exact enter/leave line numbers, module address,
raw handle, kind, changed-field list, input float32, observed delta, and the
before/after float32 values of `0x190`, `0x19c` and `0x1a0`. The classified
file's `frame`, `simulation_time`, `unit_identity` and `player_identity` are all
`null`; any non-null value would fail the check. There were no missing or extra
entries.

That agreement is regression consistency: both files derive from the same trace
under the same `mode -> field` mapping, so a match confirms reproducibility and
refutes fabricated or drifted events, not independent semantic ground truth for
the mapping itself.

## Timing hypotheses: independent results

All three claims in the prior audit remain unverified and are not promoted:

- **5.01 frames/s: not supported by this trace.** No trace record contains a
  frame index or simulation time; the frame count comes from the replay artifact
  and the interval from external playback metadata. The trace cannot test the
  ratio, and its decay observations cannot either: 19 observed suppression
  declines all fit 0.6, 0.3, 0.2, 0.1 and 0.05 value units to within 0.002
  (largest residual 0.001147), because 0.6 is itself a multiple of the smaller
  divisors. The data therefore does not identify 0.6 as a quantum, let alone one
  quantum as one engine step. `decay_summary.unique_divisor` is `null`, and no
  step rate, step count or seconds-per-quantum figure is asserted. What remains
  observed is raw wall-clock spacing: 15 short inter-impact intervals span
  0.178-0.965 s and the four long gaps 23.171-23.188 s. Because no frame or step
  counter exists, decay is not quantized on a resolvable time base.
- **Battle start at frame 2914: not supported.** The trace has no frame index and
  no replay binding. The decoder labels the frame-2914 event as a 0x13
  player-synchronization service request (`partial`), not a battle start; temporal
  proximity is not identity.
- **Three kills from three damage transitions: rejected.** Three mode-2
  applications are observed (M1 `L2520-L2521`, M3 `L2510-L2511`, M5
  `L2826-L2827`), each `0x19c` 0.0 -> 10.0. But `0x194` (`MaxDamages`) was never
  read, no destruction or removal hook was captured, and no unit identity exists.
  Accumulated physical damage is not a kill outcome. The kill field stays `null`.

A static clock-computation path was reported by the parent in this session:
`+0x1ec` is computed from a signed elapsed counter at module `+0xd0` multiplied
by float32 `0.2` at VA `0x195d768` (`0xc9f95c` -> `0xbb04d0` -> `0xaaedf0`,
stored at `0xc9f9ca`). This establishes arithmetic, not a runtime origin,
monotonicity or replay correspondence. The trace never reads `+0x1ec`, so no
timestamp is derived from it and all time fields remain `null`.

## Correction: module objects are outside the executable image

The prior audit stated that the captured module addresses lie inside the loaded
image range (base `0x400000`, size `31,883,264`). The artifact now scores that
claim from its own reads instead of asserting a verdict:

- image end = `0x400000 + 31,883,264` = `0x02268000` = 36,077,568;
- `corrections[0].observed` reports `module_addresses_checked: 6,
  inside_image: 0, outside_image: 6, minimum_offset_bytes: 1,071,544,544`;
- `status` is derived from those counts (`rejected_by_arithmetic` because
  `inside_image` is 0), and the detail sentence prints the same computed
  minimum: the closest address is 1,071,544,544 bytes from the base.

An in-image input now produces `confirmed_by_arithmetic` with an in-image
detail, and a mixed input produces `partially_confirmed_by_arithmetic`; the
"far outside" sentence is only emitted when every observed address is outside.

The in-image check is retained in `events.json` per module (`inside_image:
false`). These objects must not be described as image or `.data` residents
without a section-table or allocation capture; whether they are heap or another
region remains unknown. The hook code address `0xc95200` is inside the image
(offset 8,999,424), so the correction applies to the module objects, not the
hook.

## Limits

- Wall-clock is guest observation with probe overhead; no simulation or replay
  time is recoverable from this trace.
- The trace is not bound to the replay file by any in-band field; the replay link
  is contextual only.
- Parent recording covers 1 of 28 impact calls, so shooter/weapon causation is
  unknown for 27 and unproven for the remaining one.
- `+0x194`, `+0x1ec`, `0xc9bf20` and the destruction path were not captured.
- A completed trace is not proof that the running process loaded the supplied
  replay; do not read this report as such proof.
